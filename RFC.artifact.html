§1

Problem statement

An analyst investigating an identity starts from one node — a phone, an email, a device, a document — and walks outward: what else is this linked to, and what is that linked to. The graph is not fetched whole and it is not static. It grows under the analyst's cursor, one expansion at a time, and the interesting cases are exactly the ones where it grows fast: a device shared by four hundred accounts, a cluster that keeps unfolding four levels deep.

That shape of interaction breaks the assumption almost every graph-library demo is built on. Demos load a fixed graph once, look good, and stop. Ours has to survive:

  1. A cold load of a dense result set — the analyst pastes in a cohort, not a single node.
  2. Incremental expansion into an already-large scene — 25 new nodes arriving into a graph of 20,000 is a diff, and diffing is where these libraries differ most once a graph is being explored rather than loaded.
  3. Continuous interaction — pan, zoom, hover-to-peek — at a frame rate that does not make the analyst feel the tool is fighting them.
  4. A hard host constraint: React 16.14. Not negotiable this round, and it eliminates library options outright (§6.1).

What we actually need to decide

Not "which graph library is best" — that question has no answer. Three decisions, in this order:

#DecisionWhy it comes first
D1Where is our breaking point, per candidate?The single most useful number this exercise produces. Everything else is a tiebreak.
D2Does the rendering architecture hold — shared layer, swappable renderer?If yes, D3 is reversible and low-stakes. If no, D3 is a one-way door.
D3Which two engines go to a production spike?Two, not one — the customisation half (§6.3) can only be settled by building our real node design.

Why this needed a POC rather than a spreadsheet

Every one of these libraries advertises "handles large graphs". None publishes the number at which it stops, and none measures the case we care about — expansion into a large scene — at all. The claims are not comparable because no two vendors measure the same thing on the same data.

So the POC's product is not a pretty graph. It is a rig that renders the same graph at the same coordinates through eight libraries and reports the same numbers for each, so the comparison is between renderers and nothing else.

The load-bearing claim: every renderer is a dumb view over useGraph and takes identical props. Swapping engines is changing one lazy import. That is the property that makes D3 reversible, and it is what §6.3 is really reviewing.

Two callbacks flow the other way and they are the whole engine-specific surface:

  • onStat(updateMs) — every renderer times its own update and self-reports.
  • onViewport(handle) — { zoomBy, panBy, fit }, or null if the library has no viewport. Publishing null is itself a finding (§5.4).

3.2  The decision that makes the numbers mean anything

Every pane is handed the same graph at the same coordinates, from one shared layoutRadial — not from each library's own layout engine.

Several of these ship perfectly good layouts and a real app would use them. Using them here would make the comparison about layouts rather than renderers: eight different solvers, eight sets of constants, eight stopping rules. Timing those against each other measures eight unrelated implementations, not the question being asked. The same reasoning covers LOD, culling and the force solver — all shared code.

The honest counterweight, which belongs in any write-up: an engine that ships its own culling gets no extra credit here, and an engine with none gets to borrow ours. That is deliberate — it separates "this library is fast" from "this library ships the optimisation you would otherwise have written". Both matter; they are different questions and they get answered separately.

3.3  How the graph is actually built

Worth stating because it is the first question every reviewer asks about a synthetic benchmark: what does "50,000 nodes" mean here? synthGraph(nodes, edges) lays a spanning tree over the node count first, then adds cross-links until it reaches the edge count. Two consequences:

  • The edge count is a target with a floor of nodes − 1. A tree of n nodes is n − 1 edges, and the tree is not optional: layoutRadial places a node inside its parent's angular wedge, and a node with no path to a root has no wedge. 5,000 nodes never has fewer than 4,999 edges however low the dial goes.
  • It is also a ceiling in practice. Duplicate pairs are skipped rather than retried, so asking for far more edges than the node count supports lands short — 100 nodes asked for 100,000 edges builds 2,699.

Every scenario therefore reports graph.edges.length, never the knob, and the UI prints the overshoot next to the counts rather than silently disagreeing with the dial. Every size dial bottoms out at 0: an empty pane is a measurement — what this engine costs holding nothing — and it is the baseline the other rows are differences from.

The four cells that are artefacts, not findings

Stated here because each one otherwise reads as a result.

  1. v-network-graph drew nothing. VngGraph.jsx hard-caps at CEILING = 150 nodes and renders a refusal notice above it. So at 1,000 nodes every v-network-graph cell below is the cost of an empty pane showing a message: updateMs 0, 1.46 MB of heap, a flat 120 fps. It is not the fastest engine here; it is the one that declined to run.
  2. The negative leakMB values were a bug in the metric, and this list previously got that wrong. It called them "collection events, not memory returned". They were not. leakMB read its baseline with the base graph already on screen and compared it against a reading taken after the pane had been emptied — so every engine that retained nothing scored its own base graph as a negative leak. NVL came back at −72 MB, which is about what NVL costs to hold 1,000 nodes. Re-running with --expose-gc reproduced it exactly: that is what a sign error does, and what GC noise does not. Fixed — the baseline is now taken with an empty pane, and what the base graph costs is reported separately as baseMB (§5.3). Negative heapMB during churn is still a collection landing mid-window; that column was never the broken one.
  3. Six of eight hover rows came back unsupported — and that was this harness's bug, now found. The calibration grid was fixed at 56 × 28, one sample every 28 × 15 px, hunting for nodes about 11 px across. It stepped over them. At 4 px spacing, five of the six report hover (§5.4). The earlier claim that six libraries do not report node hover is withdrawn. A geometry hypothesis was tested and falsified along the way — the pane is fully in the viewport and all 1,568 points resolved to a real element — which was true and simply not the cause.
  4. fps is pinned at the refresh rate almost everywhere. A frameP95 of 8.3–9.4 ms is a clean 120 Hz frame. Rows reading 120 fps are not faster than 60 fps engines — they are all simply keeping up.

One conclusion this retracts. §5.5 shows NVL's zoom improving from frameP95 17.7 on canvas to 9.2 on WebGL, and that difference is indistinguishable from noise — the identical canvas configuration produced 9.2 in the first pass and 17.7 in the second. Three rules for reading anything below

  1. — is not zero. Where the browser will not report, the probe returns null. A printed 0 ms blocked would read as "never blocked", a far worse lie than "not measured here".
  2. Never quote a speed-up without its denominator. §5.5 is this rule demonstrating itself on live data.
  3. A mean hides the failure you can see. Every frame figure here is a percentile, and p95 is the headline, not fps.

ttfrMs, milliseconds to first visible render, at 1.5 edges per node. At 50,000 the ordering becomes a ranking of failure modes: NVL WebGL 1.2 s · NVL canvas 2.5 s · vis-network 5.6 s · Cytoscape WebGL 10.8 s · Cytoscape canvas unresponsive past two minutes.

The headline: NVL on WebGL renders 50,000 nodes in 1.2 seconds, and nothing else here comes close. It is faster at 50,000 nodes than Cytoscape and ECharts are at 20,000, and faster at 20,000 (480 ms) than any other engine is at 5,000. Its curve is 203 → 480 → 1,196 ms across a 10× range in nodes — 5.9× the time for 10× the work.

And the two WebGL paths are not the same kind of thing at all. Cytoscape's WebGL is a rasteriser swap underneath the same canvas geometry and hit-testing, so the CPU-side cost survives it: 3,948 ms against canvas's 4,266 at 20,000 — a 7% difference — and 10.8 seconds at 50,000. It does not move the wall. NVL's WebGL is a different renderer, and it moves the wall by roughly an order of magnitude. "Has a WebGL mode" is not a capability that means anything until you measure it.

The column that decides the canvas engines is not ttfrMs — it is the longest single task. For vis-network, Cytoscape and ECharts, the longest task at 20,000 is essentially the whole render: 1,272 of 2,170 ms, 3,479 of 4,266, 4,082 of 4,183. That is one un-interruptible block — no frame, no spinner, no cancel. NVL is the only engine here whose longest task (489 ms) is under half its total (1,028 ms), meaning it yields the thread while it works. At 20,000 nodes that is the difference between a slow load and a frozen tab.

NVL is also the only one that scales sublinearly: 6.8× the time for 20× the nodes, against 16–22× for the other canvas engines. And its heap at 20,000 is 103 MB against ECharts' 503 MB — for ECharts the memory wall arrives before the time wall does.

React Flow's breaking point is between 2,000 and 5,000, and it is not close. 10.8 seconds at 5,000 nodes — of which 10.8 seconds is one task — and at 20,000 it wedged the tab so completely that a page reload timed out after 60 seconds. That is past "slow": the tab has to be killed. It also cost the three legs queued behind it, which is why they were re-run last.

Two rows were already decided before this sweep. v-network-graph's ceiling is a hard cap in source, not a curve. And jsPlumb's breaking point is at or below 1,000, so the doubling exercise for it would start down.

ECharts' "500 absorbed" was a lucky run, and four repeats say so. Re-measured four more times on the same configuration and default backend it took 365, 310, 308 and 253 of 500 nodes/sec — so it absorbs roughly half to two-thirds of the feed, not all of it, and the single-run 500 left in this table is the outlier. Anyone reading this table before the repeats would have concluded ECharts keeps up under churn. It does not. Its frameP95 ranged 83.5–159 ms over the four runs (§5.0).

Two engines could not accept the feed at all. FusionCharts and jsPlumb absorbed 103 of 500 nodes/sec — the timer could not even fire on schedule, because the thread was never free. Both spent ~19 of the 20 seconds blocked. That is the failure mode that matters: not a low frame rate, a feed that silently falls behind.

ECharts is the surprise. Fine on cold load, fine on zoom — then blocked for 16.8 of 20 seconds under churn while still claiming 32 fps. Its own updateMs is 9 ms, so the cost is what it does around each setOption. An engine can pass the load test and fail the streaming test, and this row is why both scenarios exist.

NVL wins churn clearly — and note its updateMs of 199 ms is the highest in the table. It is doing real work per update and still not blocking, which is what an off-thread renderer buys.

The original write-up of six libraries without hover was an artefact of a fixed 56 × 28 grid, and it is now withdrawn.

But the re-run replaced one measurement problem with another, so hover is diagnosed rather than measured. Even at 4 px the hit area is under 1% for most engines, so the measured sweep cycles through a handful of distinct hit points and the engines dedupe — hence ECharts at 1 callback and React Flow at 0 where calibration had just found hits. callbacksPerMove is only trustworthy where calibration found plenty of hit points: vis-network 1.00, jsPlumb 1.00, and Cytoscape 1.00 from the first pass. Three engines that fire on every pointer transition — correct, and a React render each.

And the incidental finding is the biggest one in the section. The window is nominally 8 seconds but ends at the first animation frame after 8 s — so when it reports 70.1 s of blocked time, the sweep really did take about seventy seconds, almost entirely blocked. jsPlumb 70 s, NVL 55 s, ECharts 16 s, FusionCharts 14 s, and Cytoscape past the driver's two-minute limit. Hover traffic over a 1,000-node graph is expensive enough to lock the thread for a minute on half these engines, and it does not show up in frameP95 at all — NVL reports a perfect 9.2 ms frame while blocked for 55 s, because the frames it does present are fine and there are simply almost none of them. This is the one scenario where frameP95 is the wrong headline and blockedMs is the right one, and it is a strong argument for the debounce being non-optional rather than a tuning knob.

Three explanations were tried. Two are dead and the third is arithmetic.

  1. Geometry — falsified. The hypothesis was that the pane sat partly below the fold, so elementFromPoint returned null and the scenario fell back to the container. Measured: the pane is fully inside the viewport, all 1,568 calibration points resolve to a real element, and none resolve to the container. Not this.
  2. Untrusted events — tested, and it needed its own fix first. Every event the scenario dispatches carries isTrusted: false. Re-running with real trusted pointer input required a read seam on the hover counter, because the lab's gauge repaints on the HUD's schedule and is stale immediately after a move — a first attempt without it scored Cytoscape at 0 hits of 800 on a page where it was demonstrably firing. That was the driver, not the library.
  3. Calibration resolution — this is the real problem, and the existing numbers prove it. A node is about eleven pixels across on a fitted 1,000-node graph. The grid samples 56 × 28 points across a ~1,550 × 434 pane — one sample every 28 × 15 px — so it steps over most nodes. ECharts' measured hitArea is 0.2%: three points out of 1,568. At that density a coarser grid finds zero by chance, and an engine whose hit area is a little smaller than ECharts' finds zero at any grid density this scenario uses. Six unsupported rows are consistent with a calibration that cannot reliably locate a node, not with six libraries lacking hover.

Fix applied: the grid is now derived from the pane at ~4 px spacing rather than fixed at 56 × 28. That is affordable only because the calibration loop is synchronous and in-page. Driving the same coverage with real trusted pointer input through CDP was also built and abandoned — it is roughly 37,000 round trips per engine, minutes each — so the trust question stays open, with one data point: FusionCharts, unsupported under synthetic events, reported hover under trusted input. Results below.

What the two returned rows already say is worth keeping regardless: callbacksPerMove is the number to design against. Cytoscape reports 1.00 — a React render for every pointer transition, correct and expensive. ECharts reports 0.67, i.e. it is deduping. Both blocked heavily — 5.2 s and 1.0 s across an 8 s sweep — while reporting a healthy frameP95: hover cost lands in blocked time, not in frame percentiles, which is why frameP95 is the wrong headline for this one scenario.

The shared incremental layout — identical code for all five — costs 2 ms at 1,000, 7 ms at 5,000 and 25 ms at 20,000; it is inside every number above and never more than 2.4% of one.

At 20,000 nodes the interaction this product is built around freezes the tab for about a second per click, on every engine measured. That is the finding. It is not a ranking problem — the best engine here is ten times too slow for the interaction, and the spread between first and last engine is smaller than the gap between all of them and acceptable.

And the §5.6 Worker result does not rescue it. That moved the layout off the main thread. This is render, and it is on the main thread by definition — a canvas has to be painted from the thread that owns it.

Nor does WebGL — it makes this one worse, and the reversal is the tell. NVL on WebGL expands a 1,000-node graph in 96 ms against canvas's 97 — no difference — and expands a 20,000-node graph in 1,408 ms against canvas's 1,045. The same backend that halves cold load at 20,000 (§5.1: 480 vs 1,028 ms) costs 35% more per expansion there. That is exactly what you would expect if the scene is being re-uploaded whole on every click: WebGL is cheap to draw and expensive to re-upload, so handing it the entire graph each time pays its cost and throws away its benefit. It is corroboration for C9 from the opposite direction — the fix is not a faster backend, it is not re-handing the graph.

The RFC predicted the wrong culprit, and the numbers say so

This section used to read: "the incremental radial layout is O(n²) … expanding 25 nodes into 20,000 is the row to watch, and if it is bad, the fix is in our code, not in a library." Measured, that is backwards. The layout costs 25 ms at 20,000 — 2.4% of NVL's 1,045 ms wait. The other 97.6% is the engine's own data path, and reading the wrappers explains why:

  • VisGraph.jsx calls DataSet.update() with all 20,000 nodes on every click, having first built 20,000 fresh node objects.
  • CytoscapeGraph.jsx iterates all 20,000, calls getElementById on each and rewrites .data() on every one that already exists.

Two independently written wrappers, the same shape — because the props contract makes it the only shape available. Every renderer is handed graph, a whole new object, and has to re-derive its scene from it; styling depends on hidden and isExpanded, which can change for nodes already on screen, so the walk is not gratuitous. first→last confirms the mechanism: NVL at 20k goes 1,085 → 1,051 across the run, dead flat, so the cost tracks total graph size and not nodes added. That is the signature of a rebuild, not a diff.

So this is a §3.1 finding, not a §4 one. The one-shared-layer, dumb-renderer design is what makes the eight engines comparable at all — and it is also what caps the interaction the app ships. Cytoscape, vis-network and NVL all expose real incremental APIs (cy.add(), DataSet.update() with a delta, NVL's addAndUpdateElementsInGraph) that a "here is the whole graph" prop cannot reach. Before choosing between the three shortlisted engines, the props contract needs a delta channel — and that work is worth more than the difference between them.

Which also means: these numbers are an upper bound on the architecture, not a ceiling on the libraries. Nobody should quote them as "NVL takes a second to expand".

React Flow's row is the same lesson as §5.2, twice as loud. Its own updateMs is 1 ms at 1,000 nodes and 5 ms at 5,000 — about 1% of the wait. It is the fastest library in this table and the only one that could not complete the 20,000 run at all. React reconciling and the browser laying out tens of thousands of DOM elements is the entire cost, and no library-level benchmark would ever see it.

6.2  Scalability and performance under load

This is §5 in full, and the harness is built around one idea: find the absolute breaking point, not the average speed. Every library is fast at 200 nodes. The design decisions that make the load real rather than theatrical:

  • Cold pane for the hairball — a first render, not an update against a graph the engine already has.
  • Streaming pushes on a timer, not after each paint, with a flat node count.
  • Zoom is driven once per animation frame, so the interaction happens at exactly the rate the engine can present. Pushing transforms from a setInterval would queue work the renderer never shows and turn it into a queue-depth test.
  • Hover calibrates first. A node is ~11 px across on a fitted graph, so a blind sweep lands on one roughly never. An earlier version reported "1 callback out of 181 moves" for all eight engines — which measured the geometry of the sweep and nothing about the libraries.
  • The bench runs one engine at a time. Frame times, long tasks and heap are properties of the tab, not of a component. Eight panes sharing a main thread would produce eight rows that each read "this engine plus seven others".

6.3  Extensibility and modularity

The claim under review is §3.1: the engine is a swappable leaf, not a foundation. Evidence that it holds:

  • Eight renderers, identical props, one lazy import each. src/engines.js is the whole registry.
  • The engine-specific surface is exactly two callbacks — and a library with no viewport returns null rather than forcing a special case upward.
  • Interaction, expansion, add/delete, layout, LOD, culling and the force solver all live above the renderer and are unit-tested independently of any of them.
  • fetchNeighbors() in data.js is the only function that invents data — the single seam to swap for a real backend call.

The unmeasured half, stated plainly. Custom glyphs and edge routing are capability-matrix only (§4), not benchmarked. The spread is wide — from symbol: image://… per node (ECharts), through background-image per selector (Cytoscape), to anything React can render (React Flow) — and that last one is exactly the trade: the most customisable and the least scalable, for the same reason. An engine offering five edge-routing modes is telling you it will happily let you make it slow; curves cost significantly more maths per edge than straight lines.

This is why D3 asks for two engines, not one. Custom rendering is where canvas libraries lose most of their advantage, and how much they lose depends entirely on what our node design asks for. The only way to settle it is to implement the real design in the finalists and re-run the hairball and zoom scenarios. An unmeasured column is more honest than a guessed one — a benchmark that reports a number nobody produced is worse than one that admits a gap.

8.3  Findings already banked QUALITATIVE

Not superseded by §5 — these still stand:

  • A 10× hover improvement that had nothing to do with the graph library. 8.65 ms → 0.86 ms per hover at 159 nodes, from four fixes all in shared code: React.memo on the renderers, stable isExpanded/isPending identities, hiddenCounts batched out of an O(n²) loop, and unstable_batchedUpdates around the fetch resolution. Three of the four are React-16-specific traps that would not exist on React 18 — which is why Q3 matters.
  • The radial layout took three attempts. A top-down tree was ~19,000 px wide at 116 nodes; a leaf-count-proportional radial collapsed into a single arc because ring radius was sized off the tightest adjacent pair. What ships gives each leaf one equal angular slot. All three failure modes are pinned by tests.
  • Self-edges break every graph walk that assumes edges mean hierarchy. Four places in the shared layer had to learn to skip them. Some engines render loops natively; React Flow v9 collapses them to nothing and needs a custom edge type.
  • Inverted and surprising APIs are real cost. NVL's animated: true means "do not animate"; it never re-fits the viewport when elements are added, so an expanding graph walks off screen. React Flow v9's onElementClick fires from react-draggable's onDragStop, not the node's onClick.

8.4  Reproducing

npm install --legacy-peer-deps   # npm 11 refuses the React 16 peer graph
npm test                         # 50 assertions, shared graph + bench layers
npm run dev                      # http://localhost:5173

Then #/bench → Everything, which runs the exact matrix in §5 in under seven minutes, and #/compare → Export JSON. For the §5.6 Worker leg, select Layout & worker, tick In a Web Worker and hit All engines — Everything uses default knobs and so only ever runs the main-thread half.

Close your other tabs — frame times and long tasks are properties of the tab's main thread, and a Slack notification lands in your p95. Prefer a 60 Hz display, or state the refresh rate as §5.0 does; add --js-flags="--expose-gc" if you care about the leak column, which this pass did not.
